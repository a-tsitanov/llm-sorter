# llm-sorter

Сервис классифицирует тексты по дереву тем с помощью моделей и может расширять дерево по мере поступления новых сообщений. Источники публикуют сообщения в RabbitMQ, обработчик выбирает тему, а learner предлагает новые темы на основе накопленных текстов. Дерево хранится в SQLite.

## Требования

- Python 3.12 или 3.13, [uv](https://docs.astral.sh/uv/) и Docker Compose.
- Сервер моделей, доступный из процессов приложения. Для стандартного протокола нужны OpenAI-совместимые chat completions и embeddings; для `DECIDE_PROTOCOL=systemone` дополнительно нужен `/v1/systemone` с decision-моделью.
- Для примера с LM Studio и LiteLLM — установленные LM Studio с `lms` и модели `d1-3b`, `qwen3-vl-4b-instruct-mlx`, `qwen/qwen3.5-9b`, `text-embedding-bge-m3`. Для одновременной загрузки необходим достаточный объём памяти.

Команды ниже запускаются из корня репозитория. Если `.env` уже существует, сохраните его: он может содержать локальные настройки и секреты.

## Первоначальная настройка

1. Установите зависимости и создайте конфигурацию, если её ещё нет:

   ```bash
   make install
   test -f .env || cp .env.example .env
   ```

2. Укажите в `.env` адрес и ключ сервера моделей, имена моделей и протокол выбора темы. `.env.example` — пример с другими значениями по умолчанию; он не содержит готовый ключ локального LiteLLM. Для уже настроенного локального LiteLLM используются:

   ```dotenv
   LLM_URL=http://127.0.0.1:4001/v1
   LLM_API_KEY=<ключ локального LiteLLM>
   LLM_GUARD_URL=
   LLM_TEXT_URL=
   MODEL_DECIDE=d1-3b
   DECIDE_PROTOCOL=systemone
   MODEL_GUARD=small
   MODEL_TEXT=large
   MODEL_EMBED=bge-m3
   ```

   Ключ должен совпадать с ключом LiteLLM. Для `chat` вместо `systemone` модель выбора должна поддерживать chat completions с JSON Schema. Пустые `LLM_GUARD_URL` и `LLM_TEXT_URL` направляют все запросы на `LLM_URL`. Отдельные адреса и ключи для этих ролей доступны в `.env.example`.

3. Поднимите Docker-инфраструктуру:

   ```bash
   make up
   docker compose ps
   ```

   Compose запускает RabbitMQ, Prometheus и Grafana, но не модели и не процессы llm-sorter. Если порты RabbitMQ изменены через `RABBIT_PORT` или `RABBIT_MGMT_PORT`, приведите `RABBIT_URL` в `.env` в соответствие с опубликованным портом.

4. Подготовьте дерево. Посмотрите текущее состояние:

   ```bash
   uv run llm-sorter topics show
   ```

   Новое хранилище начинается с корня. Для работы с готовыми темами на **новой пустой базе** можно импортировать пример для синтетического набора:

   ```bash
   uv run llm-sorter topics import datasets/synthetic-v1/topics.yml
   uv run llm-sorter topics show
   ```

   Это тестовое дерево, а не универсальный набор тем. В существующую базу импортируйте данные осознанно: `--replace` архивирует текущие темы. Пустое дерево можно оставить для автоматического обнаружения тем после накопления достаточного числа сообщений.

## Локальные модели и LiteLLM

Настройка конкретной машины с LiteLLM на `127.0.0.1:4001`, загрузкой моделей через LM Studio API и запуском через macOS LaunchAgent описана в [deploy/litellm-local/README.md](deploy/litellm-local/README.md). Это отдельный экземпляр: он не изменяет другие сервисы на порту 4000. Если LiteLLM или LaunchAgent на этой машине ещё не настроены, следуйте разделу первоначальной установки в этой инструкции.

После настройки, если сервер и модели не запущены:

```bash
lms server start --port 1234 --bind 127.0.0.1
lms ps
```

Загрузите отсутствующие модели через API по инструкции локального LiteLLM, затем запустите шлюз:

```bash
launchctl kickstart -k gui/$(id -u)/local.llm-sorter.litellm
```

Команда `kickstart` применима только после установки соответствующего LaunchAgent. LiteLLM при входе пользователя запускается автоматически, но сам LM Studio и модели автоматически этой настройкой не запускаются.

Полный справочник переменных окружения, значений по умолчанию и настроек Docker Compose — [docs/configuration.md](docs/configuration.md).

## Запуск процессов

Запустите каждую долгоживущую команду в отдельном терминале:

```bash
make process    # обработчик входящих сообщений
```

```bash
make learn      # единственный learner для данной SQLite-базы
```

```bash
make feed-dir   # или make feed-tg для Telegram
```

Команды можно запускать и напрямую: `uv run llm-sorter process`, `uv run llm-sorter learn`, `uv run llm-sorter feed dir`. Останавливайте каждый процесс через `Ctrl+C`. Learner использует блокировку рядом с SQLite: для одной базы должен работать только один экземпляр. Обработчиков может быть несколько; для дополнительного на той же машине отключите его HTTP-метрики командой `uv run llm-sorter process --metrics-port 0` либо выделите другой порт.

### Проверка на файле

По умолчанию фидер читает каталог `data/inbox` (`SOURCE_DIR`). Он создаёт его при запуске. В другом терминале создайте файл с уникальным именем:

```bash
mkdir -p data/inbox
printf 'Клиент обсуждает оплату банковской картой.\n' > data/inbox/example-001.txt
```

Для `.txt` идентификатором будет имя файла без расширения. Для `.json` ожидается объект:

```json
{"id":"example-002","text":"Клиент обсуждает оплату банковской картой.","metadata":{"source":"example"}}
```

`id` должен состоять из латинских букв, цифр, `.`, `_`, `-` и не содержать `..`. Используйте уникальные стабильные ID: подтверждённые сохраняются в `SOURCE_DIR/.seen.json`; изменение содержимого файла с тем же ID не вызывает новую публикацию. Файлы не удаляются. Не редактируйте `.seen.json` во время работы фидера. Ошибочные файлы пропускаются с предупреждением.

В логах фидера появится `published <id>`. Результаты классификации отправляются в exchange `llm-sorter.classified` с routing key по пути темы и сохраняются в очереди `llm-sorter.classified.all`. Неподходящие сообщения попадают в stream `llm-sorter.other`; если дерево пустое или тема не подошла, записи в архиве классификации может не быть. Имена очередей настраиваются через `.env`.

### Telegram

Укажите `TG_API_ID`, `TG_API_HASH`, авторизованную Telethon `StringSession` в `TG_SESSION` и нужные названия папок в `TG_FOLDERS` через запятую. Сессию нужно получить и авторизовать средствами Telethon; встроенная команда её не создаёт. Храните `.env` и session как секреты. Проверить названия папок и запустить фидер:

```bash
uv run llm-sorter tg-folders
make feed-tg
```

`TG_STATE_FILE` хранит курсоры чатов, `TG_BACKFILL` задаёт число последних сообщений при первом опросе, `TG_MIN_LEN` — минимальную длину текста. Рекомендуемый `POLL_INTERVAL_S=60` снижает частоту запросов. Telegram-фидер учитывает явные включённые чаты и фильтры групп/каналов; фильтры контактов и ботов игнорируются.

## Дерево, логи и состояние

```bash
uv run llm-sorter topics show                 # дерево и routing keys
uv run llm-sorter topics log                  # история изменений
uv run llm-sorter topics export -o topics.yml # экспорт
uv run llm-sorter topics --help               # add, edit, move, archive, import
uv run llm-sorter topics edit cards --title "Банковские карты" --description "Платёжные карты" --guard "Это сообщение о банковских картах?"
uv run llm-sorter topics edit cards --example "Дебетовые карты" --example "Кредитные карты"
uv run llm-sorter history read --topic finance.cards --days 30 --limit 100
uv run llm-sorter history replay --days 30  # повторно отправить историю на классификацию

tail -f ~/.local/share/llm-sorter/litellm.log # локальный LiteLLM
docker compose logs -f rabbitmq               # инфраструктура
```

`topics edit` сохраняет изменение и новую ревизию в SQLite; обработчики подхватят её после обновления кеша. Ранее опубликованные результаты автоматически не переклассифицируются. Для проверки существующих определений используйте `topics export` и `topics log`. Отключить проверку конечной темы можно через `GUARD_ENABLED=false`; результат будет содержать `gate: skipped`.

История хранится в отдельном stream `CLASSIFIED_HISTORY` 30 дней от публикации, включая сообщения без темы. Ограничение `HISTORY_MAX_BYTES` может удалить записи раньше; повторная классификация создаёт новую запись. `history read` просматривает весь доступный stream, выбирает последний результат для каждого ID по ревизии и времени, затем фильтрует тему. Команда выводит JSON Lines, включая `truncated`: такой результат неполный. История начинается после включения новой версии; прежняя очередь `classified.all` не импортируется автоматически. `history replay` отправляет исходные сообщения из истории в inbox; при новой теме без неё в фильтре надо переобрабатывать всю историю. Повторная доставка возможна, потребителям нужна идемпотентность.

По умолчанию `MULTI_TOPIC=true`: на каждом узле модель последовательно выбирает варианты, исключая уже выбранные, до `other` или `MULTI_MAX_CHOICES`. Если включён guard, каждый конечный лист проверяется отдельно. Модель может остановиться на `other` раньше, чем выберет все подходящие темы; качество нужно оценивать на размеченных примерах. Когда доступные ветки не проверены из-за лимита или ошибки модели, история помечается `truncated: true`. На каждый лист публикуется отдельное событие с его routing key, а в историю — один снимок всех найденных тем.

При обновлении остановите старые процессы и обновите learner и обработчики вместе: старые версии не понимают новые поля записей stream. Уже найденная ветка сама по себе не доказывает наличие неизвестной второй темы: автоматическое обнаружение всё ещё зависит от материала, попавшего в `other` или в буферы листьев.

Процессы `process`, `learn` и `feed` пишут логи в свои терминалы. RabbitMQ Management по умолчанию: `http://localhost:15672` (`guest` / `guest` при подключении с localhost); Grafana — `http://localhost:3000`, Prometheus — `http://localhost:9090`. Если порты изменены, используйте значения из конфигурации. Архив очереди можно просмотреть в RabbitMQ Management; получение сообщений через UI с подтверждением удаляет их из очереди, поэтому выбирайте режим повторной постановки, если сообщение нужно сохранить.

При остановке `make down` контейнеры Compose останавливаются, но именованный том RabbitMQ сохраняется. RabbitMQ хранит очередь, архив и stream — это состояние системы; SQLite хранит дерево и позицию learner. Не удаляйте том и не меняйте настройки retention существующего stream без понимания последствий. Изменение пути темы меняет routing key подписчиков. Доставка выполняется как минимум один раз: потребителям событий по темам нужно устранять дубли по паре `id` и ID темы, учитывая `tree_rev`; полный актуальный список тем берётся из снимка истории.

## Проверки и устранение неполадок

```bash
make lint
make typecheck
make test      # unit-тесты, без RabbitMQ
make test-int  # интеграционные тесты, нужен запущенный RabbitMQ
```

| Признак | Что проверить |
|---|---|
| Нет подключения к моделям | `LLM_URL`, ключ, запущенные модели, журнал LiteLLM; `/v1/systemone` нужен для D1. |
| Сообщения не классифицируются | Логи фидера и обработчика, очередь inbox, дерево `topics show` и возможность результата `other`. |
| Нет новых тем | Запущен ли learner, накоплен ли порог новых сообщений, есть ли свободные слоты и допустимая глубина дерева. |
| `PRECONDITION_FAILED` от RabbitMQ | Все процессы должны использовать одинаковые `OTHER_MAX_AGE` и `OTHER_MAX_BYTES`; параметры существующего stream не меняются простым перезапуском. |
| Занят порт метрик | Измените `METRICS_PORT` / `LEARNER_METRICS_PORT` или используйте `--metrics-port 0`. |
| Повторный файл не отправляется | Проверьте его ID и состояние `SOURCE_DIR/.seen.json`. |

Как добавить новый источник — [docs/feeders.md](docs/feeders.md). Архитектурные решения и текущие ограничения подробнее описаны в [CLAUDE.md](CLAUDE.md) и [дизайне v2](docs/superpowers/specs/2026-10-23-llm-sorter-v2-design.md).
