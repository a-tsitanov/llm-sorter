# llm-sorter v2: упрощение до трёх слоёв

Дата: 2026-10-23. Заменяет [дизайн 2026-10-19](2026-10-19-llm-sorter-design.md) и его [план](../plans/2026-10-19-llm-sorter.md).

## Зачем

Первая версия (Temporal + Postgres + RabbitMQ) оказалась слишком сложной в эксплуатации. Тест на Telegram-постах (2026-10-22) потребовал отдельных БД, namespace Temporal, очереди и трёх процессов; на выходе — тысячи висящих workflow, которые надо разбирать вручную. Кроме того, цель — высокая скорость обработки, а Temporal даёт накладные расходы на каждый шаг (история событий, workflow task на каждую activity), не давая ничего, чего нельзя получить от ack в RabbitMQ.

LLM будет на отдельном мощном сервере (OpenAI-совместимый API, например vLLM), поэтому её пропускная способность в дизайне не ограничение. Узким местом не должна стать и обвязка.

## Цели

- Три независимых слоя-процесса: **фидеры** → **обработчики** → **дообучение**, связанные только через RabbitMQ и SQLite.
- Конфиг (дерево тем) в SQLite. Минимум зависимостей и инфраструктуры: из сервисов нужен только RabbitMQ (и LLM-сервер).
- Асинхронность везде, где можно (aio-pika, aiosqlite, async OpenAI-клиент).
- Обработчики без состояния: их можно запустить сколько угодно экземпляров для скорости.
- Дерево растёт само: дообучение по порогу, без участия человека — и вширь (новые соседние темы), и вглубь (лист прорастает подтемами).
- Нагрузка: 50–60 тыс. сообщений в сутки (в среднем ~0,7 сообщения/с, пики — на порядок выше). Для обвязки это немного: один процесс-обработчик и одно дообучение должны справляться с запасом; нагрузочные тесты не нужны, достаточно smoke-теста пропускной способности на фейковых моделях.

## Не-цели

- Снимки версий дерева и откат к старой версии. Вместо этого — журнал изменений.
- Встроенные действия (save/translate/annotate/notify). Результат публикуется в RabbitMQ, что с ним делать — решают подписчики.
- Exactly-once доставка. Гарантия — at-least-once, подписчики отбрасывают дубли по `id`.
- Хранение текстов сообщений в SQLite.
- Уведомления подписчиков о новых темах (можно добавить позже поверх журнала).

## Анти-цели (провал, даже если работает)

- Сообщение молча теряется (не попало ни в `classified`, ни в `other`).
- Сообщение бесконечно гоняется по кругу `other` → перегон → `other`.
- Дообучение добавляет в дерево мусор: дубли соседних тем, `guard: 'yes'` и подобные пустые проверки (было в тесте 2026-10-22).
- Для локального запуска снова нужно поднимать что-то кроме RabbitMQ.

## Схема

```
фидер TG ─┐
фидер dir ┴─► [queue: llm-sorter.inbox] ─► обработчики (N процессов × M корутин)
                                              │ спуск root → … → лист → гейт
                       ┌──────────────────────┴───────────────┐
                       ▼ гейт пройден                          ▼ тема не найдена / гейт отказал
     [exchange: llm-sorter.classified, topic]       [stream: llm-sorter.other]
       routing key = путь темы (finance.banks.cards)  заголовок node = узел, где застряло
       ├─► [queue: llm-sorter.classified.all] (#)                 │
       └─► очереди подписчиков (finance.#, …)                     ▼
                                                     дообучение (1 процесс)
                                                     копит по узлам → порог → кластеры →
                                                     LLM предлагает темы → проверки →
                                                     INSERT в SQLite, tree_rev+1 →
                                                     сообщения кластеров ─► inbox (перегон)
```

## Слой 1: фидеры

- Процесс, который читает источник и публикует сообщения в `llm-sorter.inbox` (durable queue, publisher confirms). Формат сообщения — JSON `{"id", "text", "metadata"}`; `id` по-прежнему `^[A-Za-z0-9._-]+$` без `..`.
- Фидер ничего не знает о темах. Новый источник = новый фидер.
- **Telegram** — переносится существующий `TelegramSource`/`TelethonGateway` (папки `TG_FOLDERS`, курсоры по чатам, backfill, `min_len`), вместе с тестами и командой `tg-folders`. Курсоры остаются в JSON-файле `TG_STATE_FILE` (это состояние фидера, не конфиг).
- **Каталог** — переносится `LocalDirSource` для прогонов на `datasets/synthetic-v1`.
- Общий цикл опроса (`run_poller`: ack источнику только после подтверждённой публикации) переносится как есть.

## Слой 2: обработка

- Процесс-обработчик читает `inbox` с `prefetch = CONCURRENCY` и обрабатывает до `CONCURRENCY` сообщений одновременно корутинами. Масштабирование — запуск нескольких процессов. Обработчик ничего не пишет в SQLite.
- **Дерево в памяти.** При старте читает все темы из SQLite. Перед каждым сообщением сверяет `tree_rev` (дешёвый `SELECT`, можно не чаще раза в N секунд — на усмотрение исполнителя) и при изменении перечитывает дерево. Сообщение обрабатывается целиком по одному снимку дерева в памяти.
- **Спуск.** От `root`: если у узла есть дети — decide-модель выбирает одного ребёнка или `other` (логика кандидатов и промпт берутся из текущего `classify`/`traversal`/`lmstudio`). `other` — остановка на этом узле. Дошли до листа — гейт (guard-модель отвечает на вопрос `guard` листа да/нет).
- **Итог:**
  - гейт пройден → публикация в exchange `llm-sorter.classified` (type `topic`, durable) с routing key = путь из `id` тем через точку (`finance.banks.cards`);
  - decide выбрал `other` на узле X → публикация в stream `llm-sorter.other` с заголовком `node = <id узла X>`;
  - гейт отказал на листе L → в `other` **родителя** L (заголовок `node = parent(L)`): значит, ошиблась ветка, а дообучение позже предложит соседнюю тему;
  - гейт пройден на листе L, глубина L меньше `max_depth` → кроме `classified`, копия идёт в stream `other` с `node = L`, причина `leaf` — материал для прорастания листа.
- **Порядок:** публикация с publisher confirm → только потом ack в `inbox`. Падение между ними → повторная обработка и дубль у подписчиков (at-least-once).
- **Ошибки модели:** невалидный ответ → до 3 попыток; дальше decide считается `other`, гейт — отказом, в сообщение пишется `model_error`. Недоступность LLM/RabbitMQ → сообщение не ack-ается и возвращается в очередь (nack с requeue) после паузы с backoff; сообщение не должно уйти в `other` из-за сбоя связи.
- **Невалидное тело** (JSON/схема/id) → reject без requeue → `llm-sorter.inbox.dlq` (как сейчас).
- **Сообщение в `classified`:**

```json
{
  "id": "tg-1348891598-14796",
  "text": "...",
  "metadata": {"source": "telegram", "chat_title": "...", "url": "..."},
  "topic": {"id": "cards", "path": "finance.banks.cards", "title": "Банковские карты"},
  "trail": ["finance", "banks", "cards"],
  "gate": "passed",
  "tree_rev": 17,
  "classified_at": "2026-10-23T10:12:00Z"
}
```

  В `other` — то же тело без `topic`/`gate`, но с `trail` до узла остановки, причиной (`no_match` / `gate_failed` / `model_error` / `leaf`) и `tree_rev`.
- **Архив.** Обработчик при старте объявляет exchange, stream `other` и очередь `llm-sorter.classified.all` с привязкой `#`, чтобы при отсутствии подписчиков ничего не терялось.
- **Подписчики** объявляют тот же exchange (идемпотентно), свою durable-очередь и привязку с шаблоном (`finance.#`, `*.cards`, `#`). Имя exchange — договорённость, задаётся в конфиге.

## Слой 3: дообучение

- Один процесс (единственность обеспечить: single-active-consumer на stream или lock — на усмотрение исполнителя). Единственный, кто пишет темы в SQLite (кроме ручных CLI-команд).
- Читает stream `llm-sorter.other` с сохранённой позиции и копит сообщения по узлу (`node`). Повторы одного `id` — учитывается последняя копия.
- **Порог:** когда у узла X накопилось `buffer_threshold` сообщений (по умолчанию 50) и у X есть свободные слоты (`max_children`) и запас глубины (`max_depth`) — запуск discover для X:
  - эмбеддинги считаются в этот момент (embed-модель), не хранятся;
  - кластеризация (текущий `clustering`), кластеры меньше `min_cluster_size` остаются ждать;
  - для каждого кластера LLM предлагает тему (`id`, `title`, `description`, `examples`, `guard`) — текущий `propose_topic`;
  - **проверки** перед записью: дедупликация с соседями X и между предложенными (текущие `dedup_similarity`/`llm_dedup_floor` + `same_topic`), валидный `id` (латиница, нормализация, уникальность среди соседей), **осмысленный `guard`** — вопрос, а не `yes`/`да`/пусто (критерий — на усмотрение исполнителя, но с тестами на значения из теста 2026-10-22);
  - прошедшие → `INSERT` в `topics` с `parent_id = X`, запись в журнал, `tree_rev + 1` — одной транзакцией;
  - сообщения из принятых кластеров публикуются обратно в `inbox` с заголовком `x-reprocess` + 1. Перегон начинается от `root`.
- **Защита от круга:** обработчик, получив сообщение с `x-reprocess >= MAX_REPROCESS` (по умолчанию 3), при повторном попадании в `other` помечает его `final_other` — дообучение такие сообщения в буфер не берёт.
- **Позиция в stream** хранится в SQLite (`learner_state`) — это «низшая» позиция, до которой все сообщения разобраны: после перезапуска чтение продолжается с неё, и ждущие порога сообщения не теряются. Сообщения, уже перегнанные, при перечитывании пропускаются (по `id` + позиции перегона; механизм — на усмотрение исполнителя).
- **Ретеншн stream:** по сроку или объёму (`x-max-age`, `x-max-length-bytes`, по умолчанию 30 дней / 10 GB). Что старше — Rabbit удаляет сам.
- Если X упёрся в `max_children`, а буфер не пуст — лог-предупреждение (аналог текущего `DiscoverBlocked`).
- **Порог считает только новое.** После discover узла X сообщения, которые попали в отклонённые или слишком мелкие кластеры (в том числе дубли существующей темы), помечаются как уже рассмотренные и не засчитываются в порог X повторно; следующий discover X запускается, когда наберётся `buffer_threshold` *новых* сообщений. Иначе отказы гейта L, кластеризуемые в дубль L, запускали бы discover бесконечно (замечание рецензии).

### Прорастание листа

- Буфер листа L — сообщения с `node = L`, причина `leaf` (классифицированы в L, гейт пройден). Порог, кластеризация, предложения и проверки — те же, что для `other`, с родителем = L и соседями = пусто (подтемы сравниваются друг с другом и с L).
- Лист делится, только если прошли проверки **не меньше двух** подтем: одна подтема, совпадающая с L по смыслу, ничего не даёт. Иначе L остаётся листом, сообщения помечаются рассмотренными.
- После деления L становится внутренним узлом: у него появляется неявный `other`, гейт L больше не используется (гейт есть только у листьев). `guard` L сохраняется в строке темы на случай, если подтемы позже архивируют.
- **Уже классифицированные в L сообщения** из буфера перегоняются через `inbox` (как перегон из `other`, с `x-reprocess` + 1): они спускаются глубже и публикуются в `classified` повторно с новым путём и большим `tree_rev`. Подписчики при дубле `id` считают актуальной запись с большим `tree_rev`. Это решение автора дизайна (см. ниже).

## SQLite

Файл `SQLITE_PATH` (по умолчанию `./data/sorter.db`), режим WAL (обработчики читают, пока дообучение пишет). Доступ через `aiosqlite`, схема создаётся кодом при старте (без alembic), с версией схемы в `PRAGMA user_version`.

```
topics(id TEXT PK, parent_id TEXT NULL REFERENCES topics,
       title, description, examples JSON, guard TEXT,
       origin 'manual'|'discovered', max_depth INT NULL,
       created_at, archived_at NULL)
settings(key PK, value JSON)          -- max_depth, language, discover.*
meta(tree_rev INT)                    -- счётчик изменений дерева
changelog(id PK, at, actor 'learner'|'cli', op 'add'|'move'|'edit'|'archive', topic_id, details JSON)
learner_state(key PK, value)          -- позиция в stream и т.п.
```

- Изменения дерева — инкрементальные: новая тема = `INSERT`, перелинковка = `UPDATE parent_id`, удаление = `archived_at`. Каждое изменение пишет `changelog` и увеличивает `tree_rev` в одной транзакции.
- Снимков и отката нет.
- `id` темы стабилен и уникален глобально (он входит в routing key). Перелинковка меняет путь темы → подписки на старый путь перестанут её получать; это фиксируется в журнале.

## CLI

- `feed tg` / `feed dir` — фидеры; `tg-folders` — список папок.
- `process` — обработчик; `learn` — дообучение.
- `topics show` — дерево с путями routing key; `topics add / move / edit / archive` — ручные правки (пишут журнал и `tree_rev`); `topics import / export` — YAML для засева дерева (например, под synthetic-датасет).

## Решения исполнителя (call)

Помечено выше; сводно: частота проверки `tree_rev`, механизм единственности дообучения и пропуска уже перегнанных сообщений, критерий осмысленного `guard`, переименование `lmstudio`, сохранение метрик и слоёв.

Решения автора дизайна по итогам рецензии (не обсуждались с пользователем, можно оспорить):

- **Сбой LLM/RabbitMQ — ждём, а не DLQ.** Обработчик при ошибке связи не делает requeue-кругов: приостанавливает потребление (circuit breaker: перестаёт брать новые сообщения, неподтверждённые остаются у Rabbit), проверяет доступность с backoff (1 с ×2, максимум 5 мин) и продолжает. `x-retries`/DLQ из v1 не переиспользуются; `inbox.dlq` получает только невалидные тела. Так сообщения ждут восстановления, а не попадают в `other` или DLQ из-за сбоя.
- **Сообщения в `other` не должны истечь по ретеншну.** Дообучение раз в сутки переиздаёт в конец stream ожидающие сообщения старше половины `x-max-age` (новая копия, старая учитывается как повтор), позиция чтения сдвигается. Метрика/лог: размер буфера по узлам, узлы в `max_children` с непустым буфером.
- **Перегон сообщений проросшего листа с повторной публикацией.** Альтернатива — оставить их в L — означала бы, что подписчики глубоких тем никогда не увидят старые сообщения. Цена — дубль у подписчиков с новым путём; правило «больший `tree_rev` побеждает» записывается в контракт exchange.
- **Миграции старого дерева нет.** Деревья из v1 (Postgres, `rules pull` YAML) — тестовые данные, переносить их не нужно. `topics import` принимает новый формат YAML (плоский список тем с `id`, `parent`, полями темы); `id` глобально уникален.

## Ограничения

- Все процессы (фидеры, обработчики, дообучение) и файл SQLite — на одной машине. SQLite в WAL не работает по сетевым дискам; масштабирование — процессами и корутинами на этой машине. Распределение на несколько хостов — вне рамок (потребует доставки дерева через Rabbit).
- Python `>=3.12,<3.14`, `uv`. Комментарии и документация на русском, идентификаторы на английском.
- Коммиты и push — только с явного подтверждения пользователя. В рабочей копии есть незакоммиченные правки пользователя (`clustering`, `discover`, `lmstudio`, `tree`, `ports/models`, тесты) — их нельзя потерять.
