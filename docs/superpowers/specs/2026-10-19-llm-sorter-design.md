# llm-sorter — дизайн

Дата: 2026-10-19. Статус: черновик, ждёт подтверждения.

## 1. Зачем

Поток транскрибированных разговоров нужно автоматически раскладывать по тематическому дереву
«от общего к частному» (пример: `финансы → крипта → трейдинг`) и выполнять над файлом действия,
заданные для темы (сохранить, перевести, сделать резюме, отправить в Rocket.Chat).

Дерево не пишется руками заранее: система стартует почти с пустого конфига и **сама
выращивает темы** из того, что попало в `other`. Конфиг можно править на лету, изменения
сразу вступают в работу.

## 2. Цели, не-цели, анти-цели

**Цели**
1. Каскадная классификация по дереву: на каждом уровне decide-модель (d1) выбирает ровно одну ветку.
2. Финальная проверка (guard) LLM-вызовом, что текст действительно про найденную тему.
3. Действия на листе по конфигу: `translate`, `annotate` (краткое резюме), `save`, `rocket`.
4. Автоматическое дополнение дерева новыми темами из накопленных `other` и немедленное включение в работу.
5. Горячая правка дерева без перезапуска воркеров.
6. Постоянные метрики качества отбора.

**Не-цели (сейчас)**
- Мультиклассификация: путь всегда один.
- UI для редактирования дерева (правка — YAML + CLI).
- Реальная интеграция с Rocket.Chat (только заглушка за портом).
- Оптимизация под большие объёмы — объём не критичен.

**Анти-цель (провал, даже если всё работает)**
- **Файлы скачут между темами.** Файл, однажды попавший в настоящую тему (не `other`),
  остаётся там навсегда — при появлении новых тем, правке описаний, удалении темы.

## 3. Поток данных

```
внешний HTTP-сервис транскрипций
   │  (адаптер сам опрашивает, дедуп по id файла)
   ▼
Ingest-адаптер ──► RabbitMQ (очередь transcripts)
                        │
                        ▼
              Consumer ──► Temporal: ClassifyWorkflow(file_id)   workflow_id = file_id
                                │
          фиксирует активную версию дерева на старте
                                │
          decide(level 1) → decide(level 2) → … → лист
                                │
                             guard (лист ≠ other)
                       ┌────────┴────────┐
                     да                 нет
                 actions листа     default action (save в _guard_failed)
                                │
         если лист = other  → файл кладётся в буфер этого other
                                │
         буфер достиг порога → DiscoverWorkflow(node)
                                │
         новые темы → новая версия дерева → активация →
         ReprocessWorkflow: файлы буфера перегоняются с родителя other
```

## 4. Дерево правил

### 4.1 Формат (YAML)

```yaml
version: 7                     # проставляется системой при публикации
settings:
  max_depth: 3                 # глубина по умолчанию
  discover:
    buffer_threshold: 50       # сколько файлов в other запускает discover
    min_cluster_size: 10       # минимум файлов для новой темы
    max_children: 12           # лимит детей на узел (без other)
defaults:
  guard_failed_action: { type: save, path: "_guard_failed" }

node:
  id: root
  children:
    - id: finance
      title: Финансы
      description: Разговор о деньгах, инвестициях, банках, платежах.
      examples: ["хочу открыть брокерский счёт", "какой процент по вкладу"]
      origin: manual            # manual | discovered
      children:
        - id: crypto
          title: Крипта
          description: Криптовалюты, биржи, кошельки, токены.
          children:
            - id: trading
              title: Трейдинг
              description: Торговля криптой, сигналы, плечи, стратегии.
              guard: Текст действительно про активную торговлю криптовалютой?
              actions:
                - { type: translate, to: en }
                - { type: annotate }
                - { type: save }                       # путь = finance/crypto/trading/<file_id>.txt
                - { type: rocket, channel: "#crypto-trading" }
```

### 4.2 Правила валидации
- `other` **не пишется** в YAML: загрузчик сам добавляет его к каждому узлу, **у которого есть дети**
  (и к `root` всегда). У листа `other` нет — файл, дошедший до листа, остаётся в нём.
- `X/other` — не настоящая тема, а «отстойник»: «про X, но ни одна дочерняя тема не подошла».
  Файлы в нём не финальны и могут уехать в новую дочернюю тему после discover.
- Узел имеет стабильный суррогатный `uid` (генерируется системой, хранится в YAML после `rules pull`);
  путь (`finance/crypto/trading`) вычисляется. Переименование/перенос узла сохраняет `uid`
  и его файлы. *(моё решение)*
- `id` уникален среди соседей.
- Глубина ≤ `max_depth` (может быть переопределена на узле: `max_depth`).
- `actions` — только известные типы с корректными параметрами.
- Минимальный валидный конфиг — только `root` (холодный старт: всё падает в `root/other`).
- Невалидная версия не публикуется; активной остаётся предыдущая.

### 4.3 Какие узлы проходят guard
Guard вызывается, когда путь закончился на настоящем узле (лист, не `other`). Если у узла нет поля
`guard`, вопрос формируется из `title` + `description`. Если путь закончился на `other` —
guard не вызывается, файл идёт в буфер `other`.

Guard сказал «нет» → default action (`_guard_failed`), статус файла `guard_failed` — финальный,
в буферы discover не попадает. В ReprocessWorkflow то же самое: нашёл тему, но провалил её guard —
уходит из буфера в `_guard_failed`. *(моё решение)*

### 4.4 Actions
- Выполняются цепочкой в порядке конфига; `translate` и `annotate` обогащают файл
  (переведённый текст, резюме), последующие `save`/`rocket` получают обогащённую версию.
- У узла без `actions` — ничего не делается, кроме записи классификации в БД.
- Автосозданные узлы (`origin: discovered`) создаются без `actions`; действия навешиваются руками.
- `save`: локальная ФС, корень из env, путь = путь узла в дереве, имя `<file_id>.txt`
  (+ `<file_id>.summary.txt` / `<file_id>.<lang>.txt`, если были annotate/translate).
- `rocket`: порт `Notifier`, сейчас адаптер-заглушка (логирует, что было бы отправлено: канал, текст, вложение).

### 4.5 Версии и горячая правка
- Каждая публикация — новая неизменяемая версия в Postgres (YAML хранится целиком + распарсенная форма).
- Публикуют: CLI `llm-sorter rules publish rules.yaml` (ручная правка) и DiscoverWorkflow (автоматически).
- Оптимистическая блокировка: публикация указывает `base_version`; если активная уже другая —
  отказ (CLI предлагает сделать `rules pull` и переложить правки). Discover в этом случае
  пересобирает изменения поверх свежей версии.
- `rules pull` выгружает активную версию в YAML (с discovered-узлами) — так ручная правка
  всегда стартует с актуального дерева.
- `rules rollback <version>` — делает активной прошлую версию (публикуется как новая с её содержимым).
- ClassifyWorkflow на старте фиксирует номер активной версии и идёт по ней до конца;
  уже бегущие файлы доходят по старой версии. Воркеры кэшируют распарсенные версии по номеру.

## 5. Модели

Все через LM Studio (локально, OpenAI-совместимый API). Модель задаётся в конфиге **на роль**,
чтобы легко сменить провайдера (vLLM и т.п.) без изменения ядра.

| Роль | Модель (старт) | Что делает |
|---|---|---|
| decide (d1) | Liquid LFM2 (точное имя — в конфиге) | выбор одной дочерней ветки по title/description/examples |
| guard | Qwen ~4B | да/нет: текст про эту тему? |
| translate | Qwen ~4B *(моё решение)* | перевод на язык из action |
| annotate | Qwen ~4B *(моё решение)* | краткое резюме |
| discover | Qwen ~4B *(моё решение)* | название/описание/примеры/guard для новой темы |
| embed | embedding-модель в LM Studio *(моё решение)* | эмбеддинги для кластеризации в discover |

- Транскрипты до ~8000 токенов, языки разные. Текст подаётся целиком, без нарезки;
  контекст моделей в LM Studio ≥ 12k. Embedding-модель — мультиязычная (напр. `bge-m3`).
- Описания тем discover пишет на языке `settings.language` (по умолчанию `ru`);
  сравнение текста на любом языке с описаниями — задача моделей.
- decide и guard — структурированный вывод (JSON schema; ответ decide — `id` одной из
  дочерних веток, включая `other`), `temperature: 0`.
- Ответ вне допустимого набора → ретрай; после исчерпания ретраев → `other` и метрика ошибки.

## 6. Самовыращивание дерева (discover)

Источник материала для discover — двух видов:
- **буфер `X/other`** (узел с детьми): файлы не финальны, после discover переобрабатываются;
- **лист `X`**: файлы финальны и **остаются в `X` навсегда**; используются только как образцы.
  После появления у `X` детей (и `X/other`) старые файлы не трогаются, новые файлы идут глубже.

1. Файл, чей путь закончился на `<node>/other` или на листе глубины < `max_depth`, учитывается
   в счётчике материала этого узла (Postgres).
2. Когда **новых с прошлого discover** файлов ≥ `buffer_threshold`, стартует `DiscoverWorkflow`
   (`workflow_id = discover:<node_path>` — не больше одного на узел одновременно).
   Также периодическая проверка по расписанию Temporal — подхватывает пропущенные пороги.
3. Эмбеддинги всего материала узла (включая не размещённый в прошлые разы) → кластеризация.
   Кластеры < `min_cluster_size` игнорируются; их файлы остаются в буфере до следующего запуска.
4. По каждому кластеру Qwen генерирует `id`, `title`, `description`, `examples`, `guard`.
5. Защита от дублей: новая тема сравнивается с соседними ветками (сходство эмбеддингов
   описаний + LLM-проверка); дубль отбрасывается. Лимит `max_children` соблюдается.
6. Публикуется новая версия с узлами `origin: discovered`, сразу активируется (без ручного аппрува).
7. `ReprocessWorkflow` (только для буфера `X/other`, не для листа): каждый файл буфера заново
   классифицируется **с узла `X`** по новой версии. Кто нашёл тему — уходит из буфера в неё
   (guard, actions — как обычно). Кто снова попал в `other` — остаётся в буфере.
   Reprocess запускается и после ручной публикации, если у узла с непустым `other` появились новые дети.
8. На `max_depth` discover не запускается. Узел, достигший `max_children`, — discover выключен,
   метрика + алерт «буфер растёт, места нет». *(моё решение)*

### Ручные изменения дерева *(моё решение)*
- Удаление узла/поддерева: файлы, закреплённые в нём, остаются как есть (узел помечается
  `archived`, в маршрутизации не участвует). Файлы из буферов `other` удалённого поддерева
  переносятся в буфер `other` ближайшего живого предка.
- `rollback`, убравший discovered-узлы, работает так же, как удаление. Discover может создать
  похожую тему заново — проверка дублей идёт только по живым соседям.

### Гарантия «файлы не скачут»
- Переклассифицируются **только** файлы из буфера `other`, и только внутри поддерева родителя.
- Запись «файл → настоящая тема» неизменяема. Удаление/правка темы её не трогает.
- Discover только добавляет узлы; не переименовывает, не сливает, не удаляет существующие.
- Узел, бывший листом и обросший детьми, сохраняет свои старые файлы; новые файлы идут глубже.

## 7. Метрики (Prometheus + Grafana, моё решение)

- Распределение файлов по узлам (по версии дерева).
- Доля `other` на каждом уровне/узле; размер буферов `other`.
- Доля отказов guard по узлам.
- Ошибки/невалидные ответы моделей, ретраи.
- Латентность decide / guard / actions; время прохождения файла.
- Discover: запуски, найденные/отброшенные темы, переехавшие из `other` файлы.
- **Счётчик переездов между настоящими темами — должен быть 0; >0 = алерт.**
- Активная версия дерева, частота публикаций.

## 8. Архитектура кода (гексагональная)

```
src/llm_sorter/
  domain/          # чистое ядро: RuleTree, Node, Path, TreeVersion, Classification,
                   # валидация дерева, правила обхода, правила discover-защиты
  application/     # use cases: ClassifyFile, RunActions, AccumulateOther,
                   # DiscoverTopics, ReprocessOther, PublishRules
  ports/           # интерфейсы (Protocol)
  adapters/
    inbound/       # http_poller (→ rabbit), rabbit_consumer (→ temporal), cli
    outbound/      # lmstudio (decide/guard/llm/embed), postgres (repos),
                   # fs_storage, rocket_stub, prometheus
  orchestration/   # Temporal workflows + activities — тонкие обёртки над use cases
```

Порты: `TranscriptSource`, `MessageQueue`, `DecisionModel`, `GuardModel`, `TextLLM`
(translate/annotate/discover), `Embedder`, `RulesRepository`, `ClassificationRepository`,
`OtherBuffer`, `FileStorage`, `Notifier`, `Metrics`.

Ядро не импортирует Temporal, RabbitMQ, httpx, SQL. Workflows детерминированы: всё I/O — в activities.

## 10. Входной контракт

- Сообщение в RabbitMQ: `{ "id": str, "text": str, "metadata": {...}, "received_at": ts }`.
- HTTP-адаптер сам опрашивает внешний сервис и сам контролирует дубликаты по `id`.
  Контракт сервиса пока неизвестен → порт `TranscriptSource` + адаптер-заглушка
  (читает файлы из локальной папки / выдаёт фикстуры). Реальный HTTP-адаптер — позже.
  Второй рубеж — `workflow_id = file_id` в Temporal (повтор того же id не запустит второй workflow).
