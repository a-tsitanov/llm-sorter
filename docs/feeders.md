# Как добавить фидер

Фидер получает новые тексты из внешнего источника и публикует их в RabbitMQ inbox. Встроенные источники: каталог (`feed dir`) и Telegram (`feed tg`). Для периодического источника реализуйте `TranscriptSource` и используйте существующий `run_poller`: он уже управляет порядком публикации и подтверждения.

## Контракт источника

Протокол объявлен в `src/llm_sorter/ports/io.py`:

```python
class TranscriptSource(Protocol):
    async def fetch_new(self) -> list[Transcript]: ...
    async def ack(self, ids: list[str]) -> None: ...
```

`fetch_new()` возвращает новые **и ещё не подтверждённые** сообщения. До успешного `ack()` тот же текст должен снова попасть в последующую выборку, в том числе после перезапуска процесса. `ack(ids)` сохраняет прогресс так, чтобы подтверждённые сообщения больше не выдавались. Если сообщение невозможно прочитать, не подтверждайте его по ошибке; заранее определите политику обработки некорректных данных.

`Transcript` находится в `llm_sorter.domain.messages`:

```python
from datetime import UTC, datetime
from llm_sorter.domain.messages import Transcript

transcript = Transcript(
    id="crm-ticket-123",
    text="Текст обращения",
    metadata={"source": "crm", "ticket_id": 123},
    received_at=datetime.now(UTC),
)
```

- `id` — стабильный и уникальный среди **всех** источников: префикс источника плюс его ID. Разрешены латинские буквы, цифры, точка, `_` и `-`; последовательность `..` запрещена. Для составных или произвольных ID примените стабильное безопасное кодирование или хеш.
- `text` — строка; пустые строки не классифицируются по теме и идут в `other`.
- `metadata` — JSON-сериализуемый словарь. Не добавляйте данные, которые не должны попасть в очередь и архив.
- `received_at` — время получения, желательно timezone-aware UTC. Сохраняйте оригинальное время источника отдельно в `metadata`, если оно нужно.

## Доставка и сохранение позиции

За цикл `run_poller` вызывает `fetch_new()`, затем для каждого сообщения последовательно выполняет `publisher.publish(transcript)` и `source.ack([transcript.id])`. При исключении цикл логирует ошибку и повторяется после `POLL_INTERVAL_S`; оставшаяся часть батча в текущем цикле не публикуется. Источник должен вернуть неподтверждённые сообщения снова.

При сбое между успешной публикацией и сохранением `ack` сообщение будет опубликовано повторно. Это **at-least-once**, а не exactly-once: стабильные ID обязательны, потребители должны устранять дубликаты, при повторной классификации выбирая большую `tree_rev`. В обработчике inbox подтверждается после успешной публикации результата.

Для курсора с монотонными ID возвращайте записи по возрастанию. Не сдвигайте курсор через неподтверждённые записи; если источник разбит на разделы, храните курсор отдельно для каждого. Курсор должен переживать перезапуск, сохраняться атомарно и не разделяться несколькими процессами без координации. При массовой выборке ограничивайте размер батча и не блокируйте event loop долгим синхронным сетевым запросом. Примеры: `LocalDirSource` использует атомарную замену файла со списком ID, `TelegramSource` хранит курсоры по чатам.

## Шаги реализации

1. Добавьте адаптер в `src/llm_sorter/adapters/inbound/`, например `crm_source.py`. Вынесите доступ к API и хранение состояния за интерфейсы, чтобы тестировать источник без внешнего сервиса. Сетевые таймауты, пагинацию и лимиты API задавайте явно.
2. Реализуйте `fetch_new()` и `ack()`. Сохраняйте позицию только в `ack()`, после подтверждения соответствующей публикации; особые правила пропуска записей должны не нарушать порядок.
3. Добавьте параметры источника в `AppConfig` (`src/llm_sorter/config.py`) и примеры без секретов в `.env.example`. Для секретов используйте `SecretStr`. Пишите отдельный файл состояния, чтобы источники не перезаписывали друг друга.
4. Добавьте команду `feed <имя>` в `src/llm_sorter/adapters/inbound/cli.py`. Создайте источник и передайте его существующей функции `_feed(cfg, source, stop)` внутри `_serve(main)`. Эта функция создаёт `InboxPublisher`, запускает poller и закрывает publisher. Ресурсы собственного клиента закрывайте в `finally`, как в `feed_tg`.
5. Добавьте тесты адаптера с подставным API и временным файлом состояния; при необходимости — интеграционный тест с RabbitMQ. Опишите новые параметры и команды в README.

Пример формы CLI-команды (замените `CrmSource` на свой адаптер и его реальные параметры):

```python
@feed_app.command("crm")
def feed_crm() -> None:
    cfg = AppConfig()

    async def main(stop: asyncio.Event) -> None:
        source = CrmSource(...)  # импорт и конфигурация адаптера — ваши
        try:
            await _feed(cfg, source, stop)
        finally:
            await source.close()  # если адаптер владеет сетевым клиентом

    _serve(main)
```

Это схема подключения, а не готовый CRM-клиент. Не публикуйте напрямую в RabbitMQ при использовании этого пути: `_feed` уже создаёт publisher и применяет подтверждение после публикации. Если источник работает по webhook или подписке и не подходит для опроса, можно написать отдельный inbound runner с `InboxPublisher`, сохранив те же гарантии подтверждения и безопасного завершения.

## Что проверить

| Сценарий | Ожидаемое поведение |
|---|---|
| Повторный `fetch_new()` без `ack` | Сообщение возвращается снова с тем же `id`. |
| Успешный `ack`, затем перезапуск источника | Сообщение больше не возвращается; новое сообщение выдаётся. |
| Ошибка публикации | `ack` для неотправленного сообщения не вызывается; оно возвращается на следующем опросе. |
| Сбой после публикации до `ack` | Дубликат допускается, но имеет тот же `id`. |
| Несколько разделов и частичный успех | Курсор каждого раздела не перескакивает неподтверждённые записи. |
| Некорректное сообщение или ошибка API | Ошибка видна в логах; неподтверждённые корректные записи не теряются. |

Существующие примеры тестов — `tests/unit/adapters/test_stub_source.py`, `test_telegram_source.py` и `tests/integration/test_rabbit_flow.py`. Запустите `make lint`, `make typecheck`, `make test` и при изменении взаимодействия с RabbitMQ — `make up && make test-int`.
